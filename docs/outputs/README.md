# 🧪 Validated AI Analytics Agent Outputs

This folder contains selected execution results from the **AI Analytics Agent for E-Commerce**.

These examples demonstrate that the agent does more than translate natural-language questions into SQL. It combines governed business definitions, analytical grain awareness, SQL execution, deterministic guardrails, DuckDB evidence, and result validation before producing a business answer.

The examples below were executed against the local DuckDB analytical layer built from the Olist e-commerce dataset.

# 1. Governed Average Order Value

## Business Question

> What is our average order value?

A generic LLM may interpret Average Order Value differently depending on the available context.

In this project, AOV has a governed business definition documented in `metrics.md`:

**Average Order Value = Delivered Revenue / Delivered Orders**

The agent selected the relevant AOV, order-grain, relationship, SQL-safety, and validation context before generating the query.

## SQL Executed

```sql
SELECT
    SUM(order_value) / COUNT(DISTINCT order_id)
FROM fact_customer_orders
WHERE order_status = 'delivered';
```

The query uses:

- `fact_customer_orders` because AOV is an order-grain metric
- only `delivered` orders because the governed AOV definition specifies delivered revenue and delivered orders
- `COUNT(DISTINCT order_id)` for the delivered-order denominator

## DuckDB Result

```text
137.04158575023973
```

### Validated Business Result

**Delivered AOV = $137.04**

The agent successfully reproduced the governed metric from database evidence rather than relying on a generic LLM calculation.

### What This Test Validates

- governed metric grounding
- correct order-grain source
- delivered-order scope
- SQL generation
- read-only DuckDB execution
- database-backed numerical evidence
- result validation

# 2. Repeat vs One-Time Customer CLTV

## Business Question

> How does CLTV differ between repeat and one-time customers? Use all item-bearing orders.

This test is more complex than a single KPI lookup because the requested comparison requires calculations at **two analytical grains**.

The governed definitions specify:

- Customer identity = `customer_unique_id`
- Historical CLTV = revenue generated by each customer across recorded purchases
- One-time customer = exactly one order
- Repeat customer = more than one order
- Scope = all item-bearing orders

## Analysis Plan

The agent determined that the calculation required two stages.

### Stage 1 — Customer Grain

Create one row per `customer_unique_id` and calculate:

- distinct order count
- historical CLTV

### Stage 2 — Customer-Type Grain

Classify each customer as:

- one-time customer
- repeat customer

Then aggregate to one row per customer type and calculate:

- customer count
- total CLTV
- average CLTV

This prevents customer-level calculations and segment-level calculations from being incorrectly collapsed into a single analytical grain.

## SQL Constructed

```sql
WITH entity_metrics AS (
    SELECT
        customer_unique_id,
        COUNT(DISTINCT order_id) AS order_count,
        SUM(order_value) AS historical_cltv
    FROM fact_customer_orders
    GROUP BY customer_unique_id
),

classified_entities AS (
    SELECT
        *,
        CASE
            WHEN order_count = 1 THEN 'one-time customer'
            WHEN order_count > 1 THEN 'repeat customer'
            ELSE 'unclassified'
        END AS customer_type
    FROM entity_metrics
)

SELECT
    customer_type,
    COUNT(*) AS customer_count,
    SUM(historical_cltv) AS total_cltv,
    AVG(historical_cltv) AS average_cltv
FROM classified_entities
GROUP BY customer_type
ORDER BY customer_type;
```

The SQL was constructed using planner metadata and then executed through the same read-only DuckDB database tool used by the rest of the agent.

## DuckDB Result

| Customer Type | Customers | Total CLTV | Average CLTV |
|---|---:|---:|---:|
| One-time customer | 92,507 | $12,828,351.84 | $138.67 |
| Repeat customer | 2,913 | $763,291.86 | $262.03 |

## Business Finding

Repeat customers generated an average historical CLTV of **$262.03**, compared with **$138.67** for one-time customers.

This means repeat customers had approximately **89% higher average historical CLTV** than one-time customers.

Although repeat customers represent a much smaller customer segment, their substantially higher customer-level value highlights the importance of repeat purchasing and customer retention.

- repeat vs one-time classification

# 3. Why Validation Matters

The goal of this project is not simply to demonstrate that an LLM can generate SQL.

Analytical SQL can be syntactically valid while still producing a misleading business result.

The agent therefore combines LLM reasoning with deterministic safeguards around:

- metric definitions
- table grain
- join relationships
- status scope
- output grain
- SQL safety
- database evidence
- numerical consistency

For example, when asked to calculate **AOV by product category**, the system identified a conflict between an order-grain metric and an item-grain dimension.

Because a single order can contain products from multiple categories, assigning the full order value to each category could duplicate the order-level measure.

Rather than silently returning a misleading result, the final agent requires an explicit attribution rule before performing that analysis.

# 4. Additional Validation Scenarios

The final agent was evaluated across **seven analytical and safety scenarios**, including:

| Scenario | Validation Goal |
|---|---|
| Item-bearing customer count | Basic database-backed analytical query |
| Delivered AOV | Governed metric and status-scope enforcement |
| Repeat purchase rate | Ambiguity detection and clarification |
| Repeat vs one-time CLTV | Multi-stage customer-grain comparison |
| AOV by product category | Cross-grain conflict detection |
| Revenue by seller | Required final-output-grain validation |
| Destructive SQL attempt | Read-only database protection |

These tests exposed several limitations of relying solely on small local LLMs for analytical reasoning.

The final architecture therefore uses the LLM for interpretation and explanation while combining it with deterministic planning, SQL construction for structurally sensitive analyses, safety controls, and database-backed validation.

# 5. Model Evaluation

Several local models were evaluated during development:

- Qwen3:4B
- Qwen3:1.7B
- Llama 3.2:3B
- Qwen2.5:3B-Instruct

The evaluation focused on practical agent behavior rather than a formal machine-learning benchmark.

Models were compared on:

- response time
- instruction following
- structured action/protocol adherence
- analytical grain reasoning
- SQL generation
- ability to complete multi-stage analytical questions

**Qwen3:1.7B** was selected as the final default model because it provided the best practical speed-to-capability tradeoff on the local development environment.

On a validated customer-count test, the model produced its first decision in approximately **12 seconds**.

More complex tests demonstrated that small LLMs could still fail to complete multi-stage analytical structures reliably. Instead of depending on a larger model, the final architecture added deterministic analytical safeguards around the LLM.

---

# 6. Final Agent Design

The resulting analytical workflow is:

```text
Business Question
        ↓
Grounding Selection
        ↓
Local Qwen LLM
        ↓
Analysis Planning + Guardrails
        ↓
SQL Generation / Deterministic Construction
        ↓
Read-Only Database Tool
        ↓
DuckDB
        ↓
Result & Grain Validation
        ↓
Business Explanation
```

The LLM is therefore **not treated as the source of truth**.

Business definitions come from governed project documentation, data structure comes from the analytical catalog, and numerical answers must be supported by successful DuckDB evidence.
