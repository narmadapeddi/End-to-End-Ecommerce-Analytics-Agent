# AI-Assisted Analytics Agent

## Purpose

This project extends an existing Olist analytics engineering and BI project with
a grounded, AI-assisted analytics workflow. Its purpose is not unrestricted
text-to-SQL. It answers business questions while respecting governed metric
definitions, analytical grain, table relationships, documented ambiguity, and
validated database evidence.

## Architecture

```text
Business Question
      ↓
Local LLM (Qwen through Ollama)
      ↓
Deterministic Grounding Selection
      ↓
Analysis Planning and Guardrails
      ↓
LLM Tool Request or Deterministic Query Construction where required
      ↓
database_tool.py
      ↓
DuckDB
      ↓
Result and Grain Validation
      ↓
LLM Business Explanation or Evidence-Backed Fallback
```

- **Qwen local LLM:** Interprets questions, requests analytical queries, and
  explains validated results. `qwen3:1.7b` is the default model.
- **Ollama:** Hosts the model locally and exposes its non-streaming HTTP API.
- **`agent/llm_client.py`:** Sends prompts to Ollama and returns generated text.
- **`agent/analytics_agent.py`:** Selects grounding, plans the analysis, detects
  ambiguity, applies analytical guardrails, coordinates query execution, and
  validates final claims. It can build SQL deterministically from validated
  planner metadata for structurally sensitive multi-stage comparisons.
- **`agent/database_tool.py`:** Accepts only read-only analytical SQL and runs it
  against DuckDB using a read-only connection.
- **DuckDB:** Stores the persistent local analytical database at
  `database/olist.duckdb`.
- **`docs/metrics.md`:** Authoritative business definitions, formulas, status
  scopes, assumptions, reference values, and known definition gaps.
- **`docs/data_catalog.md`:** Authoritative table purposes, grains, keys,
  relationships, appropriate uses, and safe-join guidance.
- **`agent/instructions.md`:** Operating policy governing planning, SQL safety,
  ambiguity handling, validation, and response content.

## Grounding

The three grounding documents have separate responsibilities:

- `metrics.md` governs what business metrics mean.
- `data_catalog.md` governs how analytical tables can be used safely.
- `instructions.md` governs how the agent operates.

The agent parses these Markdown files by heading and deterministically selects
sections relevant to the question. This reduces prompt size for a small local
model while retaining authoritative context. This is not vector search,
embedding retrieval, or an embedding-based RAG system.

## Agent workflow

```text
question → grounding → planning → query/tool execution → observation
         → validation → possible revision → final explanation
```

Simple analytical requests can use SQL generated by the LLM. When planner
metadata identifies a structurally sensitive multi-stage comparison, a reusable
deterministic builder constructs the required intermediate and final
aggregations. Every query still passes through the same read-only database tool.
The latest validated DuckDB observation is authoritative for numeric claims. If
valid evidence exists but the small model cannot complete the response protocol,
the agent can return a minimal deterministic response explicitly labeled as a
fallback.

## Safety and analytical guardrails

- DuckDB is opened in read-only mode.
- Only `SELECT` and read-only `WITH` queries are accepted; destructive,
  administrative, and multi-statement SQL is rejected before execution.
- Governed metric definitions are selected before calculation.
- Analytical and requested output grain are planned explicitly.
- Documented ambiguity and unresolved status scope can stop execution and
  request clarification.
- Cross-grain conflicts are detected when an order-level metric is requested by
  an incompatible item-level dimension without an attribution rule.
- One-to-many joins and repeated order-level measures are treated as
  multiplication risks.
- Queries requesting a breakdown must return and group by the requested final
  dimension; a valid overall aggregate is not accepted as breakdown evidence.
- Structurally sensitive comparisons can require separate entity-level and
  segment-level aggregation stages.
- The latest successful DuckDB result overrides stale grounding or earlier LLM
  numbers.
- Numeric claims are checked against the current observation; ratios with
  numerator and denominator fields can be reconciled deterministically.
- Rate metrics are presented as business-friendly percentages while retaining
  raw decimals for validation.
- SQL merely proposed in a final response is not treated as executed evidence.

## Validated examples

### Item-bearing customer count

The agent queried DuckDB and returned **95,420 distinct
`customer_unique_id` values** from the item-bearing order fact scope.

### Average Order Value

The governed definition is delivered revenue divided by delivered orders. The
agent applied the delivered-order scope and reproduced the validated AOV of
approximately **$137.04**.

### Repeat Purchase Rate

The agent detected that status scope was unresolved and asked whether to use all
item-bearing orders or delivered orders. With delivered-only scope supplied, it
returned approximately **3.0003%**.

### CLTV comparison

The agent first requested status-scope clarification. With all item-bearing
orders selected, it calculated historical CLTV at one row per customer before
aggregating customer segments:

| Customer segment | Customers | Average historical CLTV |
|---|---:|---:|
| One-time | 92,507 | $138.67 |
| Repeat | 2,913 | $262.03 |

### AOV by product category

The request was blocked before SQL execution. AOV is governed at order grain,
while product category exists at item grain and one order may contain several
categories. The agent required an explicit attribution rule instead of silently
duplicating order value.

### Seller revenue

The governed formula used `SUM(price)` from item-grain `fact_order_items`. An
overall aggregate was rejected because the question requested seller-level
output. The validated seller-level query returned **3,095 sellers**.

### Database safety

A destructive `DROP TABLE` test was rejected by `database_tool.py` before it
reached DuckDB. A subsequent count confirmed the analytical table was unchanged.

## Failure-driven improvements

Testing exposed practical small-model failure modes: generic metric assumptions,
silent resolution of ambiguity, stale numbers in explanations, incorrect grain,
incomplete multi-stage SQL, missing requested dimensions, and output-protocol
violations. These failures motivated deterministic grounding, planning,
grain/output checks, structured SQL construction, and evidence validation rather
than simply increasing retry counts.

## Model experimentation

Several local models were tried as implementation experiments, not as a formal
benchmark:

- **Qwen3 4B:** Too slow with the grounding context on the local machine.
- **Qwen3 1.7B:** Substantially faster and retained as the default.
- **Llama 3.2 3B and Qwen2.5 3B:** Tested on the more complex CLTV comparison,
  but neither reliably completed the full agent protocol.

These results informed the decision to combine a local LLM with deterministic
analytical guardrails.

## Limitations

- Small local models can still violate the response protocol or produce weak
  explanations.
- Deterministic guardrails cover documented and structurally sensitive cases;
  the agent is not fully autonomous.
- Historical CLTV is a descriptive sum of recorded customer revenue, not a
  predictive machine-learning CLTV model.
- There is no vector database, embedding pipeline, or semantic retrieval layer.
- The agent has no write access to the analytical database.
- Important analytical decisions still merit human review, especially when
  attribution rules or business definitions are unresolved.
